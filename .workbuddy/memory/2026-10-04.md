## 去掉 TLS，改用「快速幂 DH 密钥协商 + AES-GCM」的应用层加密（全网络收发重构）

### 目标
1. 网络收发不再依赖 TLS，改为双方用**快速幂（模幂）Diffie-Hellman** 约定加密密钥；
2. 优化整体代码逻辑；
3. 控制台版与 WPF 版保持一致。

### 方案
- 传输仍用 SignalR（保留自动重连），但改为**明文 HTTP**；机密性放到应用层。
- 握手：`GameHub.Handshake(clientPublic)` → 服务端用临时 DH 私钥算出共享密钥并回送自己的公钥；
  两端共享密钥相同 → `SessionCipher.FromSharedSecret`（HKDF-SHA256 → 32B key）派生出同一把 AES-256 密钥。
- 收发：对外只暴露 `GameHub.Call(加密信封)` 与推送 `Push(加密信封)`；
  明文结构为 `RpcRequest{Op,Payload}` / `RpcReply{Ok,Msg,Payload}` / `PushMessage{Type,Payload}`；
  线格式 `Base64(nonce12|tag16|ciphertext)`（AES-GCM，带认证）。
- DH 参数：RFC 3526 Group 14（2048 位 MODP，g=2），作为共享常量放在共享库（无需证书“约定”参数）。

### 改动的关键文件
- 新增（共享库 `Werewolf.Client.Share`）：
  - `Crypto/FastPower.cs`（从服务端移入，两端复用）、`Crypto/ModpGroup.cs`、`Crypto/DhKeyExchange.cs`、
    `Crypto/SessionCipher.cs`、`Protocol.cs`（信封 + 负载类型）。
  - `GameClient.cs` 重写：连接后自动握手；`Call`/`OnPush` 加解密；**公开 API 保持不变**
    （`ConnectAndJoinAsync/JoinAsync/StartGameAsync/NightActionAsync/VoteAsync/HunterShotAsync/ChatAsync` + 事件），
    因此 GUI 与控制台零改动即同步。
- 服务端：
  - 删除 `TlsCertificate.cs`、`Crypto/FastPower.cs`；`Program.cs` 监听 `http://0.0.0.0:5000`。
  - 新增 `CryptoSessionStore.cs`（connId→SessionCipher）、`EncryptedChannel.cs`（出站统一加密推送）。
  - `GameHub.cs` 重写为 `Handshake` + `Call`（内部分发到 join/start/night/vote/hunter/chat）。
  - `GameRoom.cs` 推送改走 `EncryptedChannel`；`Models.cs` 删除重复 DTO，改用共享库 DTO。
  - `Werewolf.Server.csproj` 增加对共享库的引用。
- 客户端默认地址/文案统一改为 `http://localhost:5000/gamehub`（控制台、LoginViewModel、LoginWindow）。
- 解决方案把 `ClientGUI.Tests` 也纳入 `.sln/.slnx`。

### 验证
- `dotnet build WerewolfGame.sln`：0 警告 0 错误。
- 逻辑 + 加密校验 **300 项断言**（新增 DH 一致性、会话密钥指纹一致、AES-GCM 往返、篡改/错误密钥失败等）。
- 界面冒烟 2 项通过。
- 真实服务端端到端联调（明文 HTTP）**18 项全绿**：4 客户端各自完成 DH 协商（指纹互不相同）、
  登录/开局/夜晚(按 ActingRole)/投票/聊天/状态推送全部经加密信道正常收发。

### 注意
- 这是**应用层加密**：SignalR 的握手与调用方法名仍是明文，只有信封内容是密文。若需全链路机密性应叠加 TLS。
- DH 私钥为进程内临时值（每次连接重新协商），未做前向保密之外的额外处理；未实现中间人防护（缺少服务端身份认证）。

## v1.4.0：落地上一轮列出的四项「后续改进」

### ① 网络身份认证（PSK 认证的 DH 握手）
- 共享库新增 `Crypto/PreSharedKey.cs`（内置密钥 + 环境变量 `WEREWOLF_PSK` 覆盖 → SHA256 作 HKDF salt）
  与 `Crypto/HandshakeCrypto.cs`（`DeriveKeys` / `Transcript` / `Proof` / `VerifyProof`）。
- `SessionCipher` 增 `FromKey(byte[])`；`FromSharedSecret(BigInteger)` 改为走同一套
  `HandshakeCrypto.DeriveKeys`（无 nonce + 默认 PSK），保持旧断言可用。
- 握手协议升级为三步（`Protocol.cs` 增 `HandshakeHello`/`HandshakeReply`）：
  `Handshake(helloJson)` → 服务端回 公钥+nonce+**服务端证明**；客户端校验后 `Confirm(clientProof)` → bool。
  `GameHub` 增 `Confirm`；`CryptoSessionStore` 增 pending 中间态与 `Promote`。
  **只有 Confirm 通过后 `Call` 才可用**（未认证连接拿不到会话密钥）。
- 会话密钥 = HKDF(DH共享密钥 ‖ 客户端nonce ‖ 服务端nonce, salt=PSK)，故不掌握 PSK 的中间人
  即使分别与两端 DH 也推导不出同一把密钥，配合 HMAC 双向校验实现防 MITM。
- 联调新增断言：把客户端进程的 `WEREWOLF_PSK` 改成错值后连接必须失败
  （实测抛出「服务器身份校验失败」）。**PSK 每次读取环境变量，可在同进程内改后立即验证。**

### ② 规则可配置化
- 共享库新增 `GameRules`（夜晚/投票/讨论/猎人秒数、`NightOrder`、`MinPlayers`/`MaxPlayers`），
  随 `GameStateDto.Rules` 下发给客户端。
- 服务端 `appsettings.json` 增 `GameRules` 节点；`Program.cs` 用
  `builder.Configuration.GetSection("GameRules").Get<GameRules>()` 绑定并注入 `GameRoomService`。
- `GameRoom` 拆出 `NightStepAsync` + 守卫/狼人/女巫/预言家四个 Step，
  按 `RoleInfo.ResolveNightOrder`（配置顺序 + 去重 + 补齐缺失角色）串行执行；
  各处超时与人数上下限全部改读 `_rules`。
- 客户端：`PhaseCountdown.Start(phase, rules)`、`ActionContext.MinPlayers`、
  `GameViewModel.CanStartGame` 加入人数判断（新增 `MinPlayers`/`PlayerCount`，玩家变化时通知）。
- **大坑（务必记住）**：`ConfigurationBinder` 会**追加**到已有的集合属性上，
  若 `GameRules.NightOrder` 初值就放一套默认顺序，appsettings 里的顺序会被拼到其后而失效
  （现象：时长生效、顺序仍是默认）。修法：集合属性初值留空，
  「缺省时的默认顺序」放到 `ResolveNightOrder` 里补齐。

### ③ 界面状态持久化

## v2.0 级改造：单服务器多房间（软件公司团队 SOP 交付）

以「产品经理 → 架构师 → 工程师 → QA」四阶段团队流程完成，产物见 `docs/multi-room/PRD.md`、
`docs/multi-room/ARCHITECTURE.md`（含交付总监裁定与验收记录 §11）。

### 架构（两层结构）
- **注册表 `RoomManager`**：`ConcurrentDictionary` 存 `_rooms`(roomId→GameRoom) / `_connRoom`(connId→roomId) /
  `_connUser`(connId→username)；纯注册表、**无后台线程**，便于测试直接 new。
- **房间实例 `GameRoom`**（**保留原类名**）：自己一把 `_sync` 锁 + 自己一份玩家/阶段/夜晚数据；
  新增 `Id/Name/HasPassword/_passwordHash/CreatedAt/EmptySince/HostUsername/PlayerCount/ConnectedCount`
  与 `VerifyPassword/GetPlayerByName/ToInfo/TouchOccupancy/ResetForNewGame`。原 `GameRoomService` 单例**已删除**。
- **房间隔离**天然成立：`EncryptedChannel` 按 connId 单发，`GameRoom.Broadcast*` 只遍历本房间 `Connected()`，
  注册表不参与推送 → A 房消息物理上到不了 B 房连接。
- 空房回收：`RoomRecycleService : BackgroundService`（`PeriodicTimer`）→ `RoomManager.RecycleExpired()`；
  `ConnectedCount==0 && now-EmptySince > EmptyGraceSeconds` 才回收（默认 60s，扫描间隔 10s）。

### 协议（复用唯一加密入口 Call，不新增 SignalR 方法）
- 新增 `Ops.RoomList/CreateRoom/JoinRoom/LeaveRoom`；`Ops.Join` **语义收敛为「账号校验」**，不再隐式进房。
- 新增 `CreateRoomPayload{Name,Password?}` / `JoinRoomPayload{RoomId,Password?}` / `RoomInfoDto` /
  `RoomListResult` / `RoomActionResult` / `ServerMessages`（统一文案常量）/ `RoomStatus`（Waiting/Running/GameOver）。
- `GameStateDto` 增 `RoomId/RoomName/HostName`（随 State 推送，房间信息不新增推送类型）。
- `GameClient`：`ConnectAndJoinAsync` → **`ConnectAndLoginAsync`**；新增 `LoginAsync/ListRoomsAsync/
  CreateRoomAsync/JoinRoomAsync/LeaveRoomAsync` + `IsLoggedIn/IsJoined(=在房)/CurrentRoomId/Name/HostName`
  + `RoomResult` record struct；`_roomId/_roomPassword` **仅内存**（重连靠它回带，房间密码不落盘）。
- 房间号 5 位，字符集 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`（31 个，排除 0/O/1/I/L），冲突重试 32 次。
- 房间密码 `RoomPassword.Hash(roomId,pwd)` = `"v2:" + HEX`，盐 `werewolf::room::<roomId>::<pwd>`，复用 `FastPower` 对齐 `AccountStore` 风格；**不出房间对象、不进列表**。

### 客户端流程变化（两端一致）
- GUI：`登录窗口(连接+账号) → 房间列表窗口(轮询/刷新/输密码加入/创建) → 主窗口(标题条显示房间号·房间名·房主)
  → 「退出房间」回房间列表（**不拆连接**）`。新增 `RoomListWindow` / `CreateRoomWindow` 及其 VM、`UiStateStore.LastRoomId`。
- 控制台：登录 → 房间列表（序号 / `c` 创建 / `r` 刷新 / `q` 退出）→ 进房后 `leave` 回列表。
- **破坏性变更**：`Ops.Join` 与 `ConnectAndJoinAsync` 语义收窄，旧客户端连新服务器会「登录成功但不在任何房间」，
  两端必须整体升级。

### 值得记住的经验
- **重连探针的坑**：无房间持久化时「杀掉并重启服务端」会让房间丢失，无法验证「回到原房间」；
  正解是在探针内建一个**字节透传的极简 TCP 代理**，只掐客户端链路、服务端与房间不丢。
- **注册表加入顺序**：必须「先 `AddOrReconnect` 成功、再脱离旧房间」，
  否则加入失败（满员/进行中）时会把玩家从原房间误摘。
- **裁定留痕**：`roomlist` 免登录可查是**有意为之**（需求只对「加入」设门槛），
  已记入 ARCHITECTURE §11.2，避免后续被当成 Bug 反复「修复」。

## v1.5.0：房主交接 / 房间保留 + 邀请码一键进房

需求两条：①房主退出时，房间有人则把房主转让给「第二个进房间的人」并以此类推；房间没人则（仅 GUI）弹窗问「是否保留房间」，
保留则一直留到服务器退出，不保留则服务端自动关闭。②邀请码：把「服务器地址 + 房间号 + 密码」加密封装，客户端解密后免输密码进房，GUI 与控制台都要有。

### ① 房主交接与房间保留（服务端）
- `GameRoom.OnDisconnected(connId)` 改为**返回新房主用户名**：不区分是否对局中，只要离开者是房主且房间还有人，
  就按 `_players` 的加入顺序把 `IsHost` 让给下一位（**优先仍在线的成员**，避免房主落到掉线玩家身上导致无法开局）。
- `GameRoom.Persistent`（新增，线程安全）：房主选择保留时置 true；`RoomManager.RecycleExpired()` 直接跳过持久房间。
- `RoomManager`：`Detach` 改为返回 `(room, player, newHost)`；新增 `LeaveRoom(connId, keepRoom)` →
  返回 `(room, player, newHost, roomClosed)`（**房间空且有成员离开后**才判定保留/关闭）与 `CloseRoom(roomId)`。
- `GameHub.HandleLeaveRoomAsync(payload)` 解析 `LeaveRoomPayload{KeepRoom}`，广播「离开」「👑 新房东」「房间已关闭」；
  `OnDisconnectedAsync` 同样广播新房主。
- **两条空房路径要分清**：主动退出 + 不保留 = **立即关闭**；掉线留下的空房 = 仍走宽限期回收。
  （原先唯一的「宽限期回收」测试因此要改用 `LeaveByConnection` 触发，已同步修正。）

### ② 邀请码（纯客户端，服务端零改动）
- 新增 `Werewolf.Client.Share/InviteCode.cs`：`InvitePayload{Url,RoomId,Password?,RoomName?}`、
  `Create/TryParse/LooksLikeCode`，线格式 `WW1:` + Base64Url(nonce|tag|ciphertext)（AES-GCM 复用 `SessionCipher`）。
- 密钥 `HKDF(PSK, info="werewolf-invite-v1")`：**同部署内互通**，换了 `WEREWOLF_PSK` 就解不开；
  码内**不含账号**，拿码者仍需自己登录（房主身份不会被冒领）。
- `GameClient`：`CreateInviteCode()`（密码取自内存 `_roomPassword`）、静态 `TryParseInvite`、
  `JoinByInviteAsync(payload)`（地址不同则 `ConnectAsync` 新地址 + 用内存账号重新登录 + `JoinRoomAsync`）。
- GUI：主窗口菜单「游戏 → 生成邀请码」（Ctrl+I，自动进剪贴板）、`KeepRoomWindow` 弹窗、
  登录窗口与房间列表窗口各加一个邀请码输入框；`App.RunRoomLoop` 若登录后已在房间则**跳过房间列表**直进主窗口。
- 控制台：启动时可直接粘贴邀请码代替服务器地址；房间列表 `j` 指令；房内 `invite` 指令；`leave` 固定按「不保留」。

## v1.5.1：三个用户上报问题的修复

### 关键根因（值得记住）
**客户端的「初始状态」不能依赖服务器在进房时推一次。** 进房（createroom / joinroom）发生在
房间列表窗口里，而主窗口在那之后才创建 → 服务器那次状态广播**没人订阅** → 之后若房间再无事件，
主窗口永远拿不到状态：玩家列表空白、`IsHost` 恒为 false（房主看不到「开始游戏」、
`NeedsKeepRoomDecision` 短路为 false → **「是否保留房间」根本不会被调用**）。
一个根因同时造成用户上报的第 1、3 两个现象。

**修法**：
- 协议新增 `Ops.State`（`roomstate`）；服务端 `GameRoom.SnapshotFor(connId)`（锁内取该连接视角的快照）
  + `GameHub.HandleState()`；`GameClient.RefreshStateAsync()` 并把最近一份状态缓存在 `LastState`。
- `GameViewModel` 构造时用 `_client.LastState` 即时回填，`OnLoaded` 再主动拉一次；
  `OnStateReceived` 拿到带房间号的状态时补 `IsJoined = true`（不再依赖构造时机）。
- 抽出 `ResolveKeepRoom()` 便于回归断言。

### 剪贴板问题
- 环境实测：本机 `Clipboard.SetDataObject` 抛 `OpenClipboard 失败 (0x800401D0 CLIPBRD_E_CANT_OPEN)`
  —— 复现了用户上报的「邀请码无法复制」。
- 新增 `ClientGUI/Services/ClipboardHelper.TrySetText`（6 次重试）；失败时不再假装成功。
- 新增 `Views/InviteCodeWindow`：**独立窗口 + 只读可选中文本框 + 复制按钮**，取代原来的 `MessageBox`
  （弹窗里的文字无法用鼠标选中，复制失败时用户就彻底拿不到码了）。Esc 关闭。
- 界面冒烟加了剪贴板探针：写不进去时**安全降级**并打印环境限制，不作为失败（测试宿主没有消息循环，
  OLE 剪贴板必然失败；真实客户端有消息循环）。

## v1.6.0：亮色主题（可切换 / 跟随系统）+ 邀请码窗口卡顿修复

### 邀请码窗口卡顿（用户上报）
- 现象：点「生成邀请码」后窗口要卡好几秒才显示。
- 根因：窗口 `Loaded` 里**同步**调 `Clipboard.SetDataObject`，而 WPF 的 Clipboard 内部**自带重试**
  （最多约 10×100ms ≈ 1 秒），我在外层又套了 6 次重试 ×70ms → 最坏阻塞约 6 秒，正好卡在窗口首帧。
- 修法：打开窗口**不再自动复制**（只显示 + 全选），复制改到用户点按钮时执行，
  复制前先把「正在复制…」渲染出来（`Dispatcher.Invoke(..., DispatcherPriority.Background)`）；
  `ClipboardHelper` 外层重试收敛到 2 次。

### 主题系统
- 拆成四份字典：`Colors.Dark.xaml` / `Colors.Light.xaml`（颜色唯一定义处，键名两套必须一致）、
  `Converters.xaml`（原 Palette 的转换器）、`Controls.xaml`（原 DarkTheme 的控件样式）、`Panels.xaml`。
  删除了 `Palette.xaml` 与 `DarkTheme.xaml`。
- **关键改造**：把全部颜色引用改成 `{DynamicResource ...}`（此前是 `{StaticResource ...}`），
  并把 54 处硬编码 `#RRGGBB` 映射成语义色键（用 sed 按 `Background|Foreground|BorderBrush|Value` 四种属性精确替换，
  `Color=` 保留给投影）。颜色统一挂在 **Application 级**，因此切换时只需替换那个资源槽位，
  已打开的窗口会自动重新求值 → **不用遍历窗口、也不用重建样式**。
- `Services/ThemeManager.cs`：`Initialize/SetTheme/Preference/IsDark`；「跟随系统」读注册表
  `AppsUseLightTheme` 并用 `DispatcherTimer` 4 秒轮询（不引入 SystemEvents 依赖）；偏好存 `ui-state.json.Theme`。
- 界面入口：主窗口「视图 → 主题」（跟随系统 / 浅色 / 深色）。
- **新增自维护测试**：`--ui` 冒烟会扫描 `ClientGUI/**/*.xaml`（先剥掉 XML 注释）里所有
  `{DynamicResource *Brush}` 键，校验两套配色都定义了 → 漏加颜色即失败。
  另外校验两套字典键集合完全一致、切换后 `BgBrush` 真的变了、深色比浅色暗、真实窗口跟随换色。

## v1.6.1：二级菜单深色背景修复 + SettingsWindow
