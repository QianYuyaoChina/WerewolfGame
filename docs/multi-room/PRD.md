# PRD：多房间架构改造（Werewolf.Server）

> 类型：增量 PRD（基于现有单房间项目）　作者：产品经理 许清楚（Xu）　版本：v1.0

## 0. 项目信息

- **Language**：中文
- **Programming Language**：沿用现有技术栈 —— C# / .NET 8、ASP.NET Core + SignalR、WPF（客户端 GUI）、控制台（客户端 CLI）（**不使用** Web 前端）
- **Project Name**：`werewolf_multi_room`
- **原始需求复述**：
  对现有狼人杀项目做系统性改造，使**一台服务器可同时承载多个互不影响的房间**。具体包含：
  1. 服务端实现多房间支持，同一服务器可并行运行多个房间，房间之间相互隔离，一局结束后可自动重置；
  2. 提供房间管理能力，玩家可查询服务器上当前所有房间；
  3. 房间支持密码机制，输入正确密码后方可加入；
  4. 客户端（GUI 与控制台）提供房间列表展示界面，可浏览房间、输密码加入、并支持创建房间（创建时可设置房间密码）；
  5. 明确需要改动的模块、各端交互流程与接口设计，并保证改动后各功能一致可用。

## 1. 背景与目标

**一句话产品目标**：把「一台服务器 = 一个房间」升级为「一台服务器 = 多个互不影响的房间」，让玩家可以创建/发现/带密码加入房间，并通过房间自管理支撑更大规模的同时在线。

**现状（问题）**：`GameRoomService.Room` 是唯一 `GameRoom` 单例，所有连接共享一个房间；`Ops` 只有 `join/start/night/vote/hunter/chat/ping`，`JoinPayload` 仅含账号密码，客户端登录即「连接 + 加入唯一房间」，没有房间概念。

**成功指标（可验证）**：
1. **多房间并行**：同一服务器上可同时存在 ≥2 个房间，各自独立开局、独立推进阶段、互不串消息（A 房消息不出现在 B 房）。
2. **房间可见**：任意客户端可在房间列表看到服务器上全部房间（房间号/名称/人数/状态/是否加密）。
3. **密码门禁**：无密码房间不需要密码即可加入；有密码房间错误密码一律无法加入并返回统一提示文案；正确密码可正常加入。
4. **自动重置**：任意房间一局结束（`GameOver`）后，无需重启服务即可在该房间**再次开局**；空房间可被回收并从列表移除。
5. **两端一致**：GUI 端与控制台端都能完成「浏览房间 → 创建房间 → 加入房间 → 退出房间回到列表」全流程，行为一致。

## 5. 关键规则定义

### 5.1 房间号生成与展示

- **格式**：**5 位**大写字母数字可读码，字符集排除易混淆字符 `0/O/1/I/L`，即使用 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`（31 字符）。
- **唯一性**：在服务器当前存活房间范围内保证唯一；重复则重新生成（上限重试若干次后报错）。
- **展示**：列表与房间头一律显示该房间号；房间号即房间的**唯一标识**（同名房间靠它区分）。
- **推荐值**：长度 **5**（约 2.8×10⁷ 组合，短期足够；比 4 位更抗猜测）。

### 5.2 房间密码的存储与校验

- **不得明文存储**：服务端房间对象仅保存密码的**哈希摘要**，任何日志/推送/列表接口都**不得**包含明文密码或哈希。
- **加盐**：哈希输入包含房间号作为盐（如 `werewolf::room::<RoomId>::<password>`），保证**同一密码在两个不同房间注册产生不同的存储值**，且同一密码在客户端不落盘。
- **可验证要求**：
  1. 无密码房间：`HasPassword=false`，校验一律放行（「不生效」）。
  2. 有密码房间：错误密码返回**统一文案「密码错误」**，不区分空密码/错误密码。
  3. 存储值不含明文，且同密码不同房间存储值不同（可用测试断言）。
- **推荐算法**：复用 `AccountStore` 的哈希风格（`SHA-256 + v2: 前缀`，或等价的带盐单向哈希）；房间密码用**短生命周期内存态**即可，无需落盘。

### 5.3 「结束后自动重置」的确切含义

1. **触发**：房间内 `Phase` 进入 `GameOver`（已有胜负判定逻辑触发）。
2. **状态复位**：`_running=false`，`Phase` 回到 **`Waiting`（等待中）**；清空夜晚/投票/猎人等临时数据。
3. **玩家保留**：**保留**本房间内玩家（重开无需重新加入）；重开一局时按现有逻辑重置每人存活/药水等状态并**重新分配身份**。
4. **房主保留**：房主资格保留给原房主，除非其已离开（离开则按 §5.5 转移）。
5. **何时从列表移除**：房间**不因一局结束而移除**；仅当房间内**已无在线玩家且超过宽限期**（P1-4，建议 60 秒）时回收并从列表移除；房主「退出房间」使房主无人在线时同理。
6. **可再次开局**：回到等待中后，人数满足 `MinPlayers` 且由房主调用 `start` 即开启新一局。

### 5.4 房间状态在列表中的呈现

| 内部状态 | 列表显示 | 判定依据 | 可否加入 |
|----------|----------|----------|----------|
| 等待中（未开局） | `等待中` | `Phase==Waiting` 且 `!_running` | ✅ 可加入（受人数上限与密码约束） |
| 游戏进行中 | `游戏进行中` | `_running==true` | ❌ 不可中途加入（提示「游戏进行中，无法加入」） |
| 已结束待重开 | `已结束待重开` | `Phase==GameOver` 且 `!_running` | ✅ 可加入（等同等待中） |

- 列表对每个房间附加：`人数/上限`、`是否加密(🔒/-)`、`房主`（取该房间 `IsHost` 玩家名）。

### 5.5 边界规则

| 场景 | 处理 |
|------|------|
| 同一账号重复加入**同一房间** | 视为**重连**：恢复该玩家连接与身份（沿用现有 `AddOrReconnect` 语义），补发身份私聊；不新增玩家。 |
| 同一账号在**另一房间** | 允许（账号全局唯一，房间内身份独立）；若已在其他房间则先退出该房间再加入。 |
| 已开局房间中途加入 | **不允许**，返回「游戏进行中，无法加入」。 |
| 房间满员 | 返回「房间已满（最多 N 人）」，沿用 `GameRules.MaxPlayers`。 |
| 无密码房间的密码校验 | **不生效**：即使传入密码也被忽略，直接放行。 |
| 房主离开（未开局） | 房主资格转移给房间内**最早加入**的在线玩家；房间空则回收。 |
| 房间号不存在 | 返回「房间不存在或已关闭」（加入失败）。 |

| Q3 | 「自动重置」是否保留玩家？ | **保留**玩家与房主；仅重置局内状态并重新分配身份；房间**不因结束而移除**，仅空房超宽限期回收（建议 60 秒） |
| Q4 | 已开局房间能否中途加入 / 是否要求房主开局？ | **不可中途加入**；**仅房主**可 `start` 开局（沿用现状） |
| Q5 | 房间名重复 / 同账号多房间？ | **允许同名**，以房间号为准；同账号**允许**在不同房间（每次仅在一个房间） |

## 7. 改动模块与接口设计要点（对应要求 5）

> 仅为**接口与模块层面的设计约束**（不含实现代码），用于架构师拆解与工程师落地；详细设计以架构师方案为准。

### 7.1 需要改动的模块

- **服务端 `WerewolfGame/`**
  - `GameRoomService`：由「单个 `Room`」→「房间注册表 `ConcurrentDictionary<RoomId, GameRoom>`」+ 创建/查询/回收/查找 API。
  - `GameRoom`：新增 `RoomId / RoomName / HasPassword / 密码哈希 / 房主管理`；内容逻辑与推送保持按房间隔离。
  - `GameHub`：`Ops` 分发新增 `roomlist / createroom / joinroom / leaveroom`；`join` 语义收敛为「账号校验」（不再隐式加入房间）。
  - `Models.cs`：`Player` 增加房间归属；新增房间摘要模型。
- **共享库 `Werewolf.Client.Share/`**
  - `Protocol.cs`：新增 `Ops.RoomList/CreateRoom/JoinRoom/LeaveRoom` 及各 `Payload`。
  - `Dtos.cs`：新增 `RoomInfoDto`（房间号/名称/人数/上限/状态/是否加密/房主）；`GameStateDto`（或房间信息推送）携带当前房间号/名称/房主。
  - `GameClient.cs`：新增 `ListRoomsAsync / CreateRoomAsync / JoinRoomAsync / LeaveRoomAsync`。
- **GUI `ClientGUI/`**
  - 新增 `Views/RoomListWindow`(+ViewModel)、创建房间对话框；`LoginWindow` 登录后跳转到房间列表而非直接进主窗口；`MainWindow` 顶部状态条显示房间信息 + 「退出房间」。
- **控制台 `Werewolf.Client/Program.cs`**
  - 登录后增加房间列表渲染与「序号加入 / `c` 创建 / `r` 刷新」；新增 `leave` 指令。

### 7.2 各端交互流程

**GUI**：登录窗口（地址 + 用户名 + 密码）→ **[握手 + 账号校验]** → 房间列表窗口（浏览/刷新）→（创建房间 →）选择房间（加密则输密码）→ **加入** → 主窗口（含房间头 + 退出房间）→ 退出 → 回房间列表。

**控制台**：输入地址 → 连接 + 账号校验 → 房间列表 →（序号加入 + 密码 / `c` 创建）→ 进入房间 → 指令循环 → `leave` 回列表。

**服务端**：`join`（账号校验，返回可进入房间列表）→ `roomlist`（只读）→ `createroom`（建房间 + 设密码 → 自定义房主）→ `joinroom`（校验密码/人数/状态 → 加入）→ 既有 `start/night/vote/hunter/chat`（按房间分发）→ `leaveroom`（离开 → 触发房主转移/空房回收）。

### 7.3 一致性保障

- 房间相关**单词表**（`Ops`/`Payload`/`Dto`）只在共享库定义一次，服务端与两个客户端复用，避免字段漂移。
- 所有业务请求仍走**唯一加密入口** `Call`，新增房间操作同样加密，不新增明文通道。
- 错误文案集中约定（如「密码错误」「游戏进行中，无法加入」「房间已满（最多 N 人）」），三端一致。
- 房间状态机与「是否可加入」规则以服务端为唯一权威，客户端仅做展示与前置提示。
