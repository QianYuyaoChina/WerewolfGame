# PRD：多游戏可插拔架构（增量）—— Werewolf.Server

> 类型：增量 PRD（基于现有狼人杀项目）　作者：产品经理 许清楚（Xu）　版本：v1.0
> 上游需求：「请复用大部分代码，抽象出 api，以便添加新游戏如『谁是卧底』『海龟汤』等。」

## 0. 项目信息

- **Language**：中文
- **Programming Language**：沿用现有技术栈 —— C# / .NET 8、ASP.NET Core + SignalR（服务端）、WPF（GUI 客户端）、控制台（CLI 客户端）（**不使用** Web 前端）
- **Project Name**：`werewolf_multigame`
- **原始需求复述**：
  对现有单游戏（狼人杀）项目做增量改造，把「游戏玩法」从「房间/平台能力」中剥离开，形成一套**游戏可插拔**的抽象层；在**不破坏狼人杀现有功能与观感**的前提下，使后续能以低成本接入新游戏（先期目标：谁是卧底、海龟汤）。
- **本轮范围（已与交付总监确认，不改动）**：
  1. **只做抽象层 + 把狼人杀迁移为第一个游戏模块**，不实现任何新游戏；但交付《如何新增一个游戏》接入说明与**最小骨架示例**（文档级骨架即可，不必是可玩的新游戏）。
  2. **「海龟汤」这类非回合制问答玩法本轮不纳入**，但抽象层要**预留口子**（明确预留了什么、后续怎么接）。
  3. **双端界面策略：每游戏一套专用操作面板**。框架提供通用宿主能力（房间、聊天、玩家列表、设置等），各游戏自带自己的操作面板；**狼人杀现有界面观感保持不变**。

## 1. 背景与目标

**现状（问题）**：当前 `GameRoom` 把**房间身份**（`Id / Name / HasPassword / Persistent / 房主 / 在线人数`）与**狼人杀玩法**（夜晚顺序、女巫解药毒药、猎人开枪、投票、胜负判定、`Phase` 状态机）混在一起；`Ops` 里的 `start/night/vote/hunter` 与 `GameStateDto` 的 `Phase/YourRole/ActingRole` 都带狼人杀语义；`GameRules` 也是狼人杀专用。结果是「加一个游戏」= 「动房间管理、动协议、动界面」，复用率低、回归风险大。

**一句话产品目标**：把「一台服务器 = 一堆狼人杀房间」升级为「一台服务器 = 一个多游戏房间平台」——房间只负责**承载**（房间号、密码、房主、玩家、聊天、邀请码、重连），**玩法**由可插拔的游戏模块提供，使新增一个游戏**只需按固定接入点补齐游戏自己的部分，无需改动任何既有平台模块**。

**成功指标（可验证）**：

1. **狼人杀零回归**：现有全部狼人杀能力（多房间并行、房间密码、邀请码一键进房、房主交接与房间保留、断线重连、亮/暗主题 + 跟随系统、设置窗口 `Ctrl+,`、GUI 与控制台两端）在新架构下**行为完全不变**；`ClientGUI.Tests` 的 `--ui/--server/--rooms/--lifecycle/--hostinvite/--reconnect` 全部通过。
2. **新增游戏不动既有模块**：新增一个游戏时，改动文件清单**不包含**下列既有模块——房间注册表（`RoomManager`）、账号/登录、邀请码（`InviteCode`）、断线重连、主题/设置、大厅/房间列表宿主逻辑。即**既有平台模块改动数 = 0**（新游戏只新增文件 + 在注册点登记一条元数据）。
3. **接入点有明确上限**：新增一个游戏需要触碰的接入点 **≤ 5 类**（见 §5.4），可在评审时逐条核对，避免「抽象层没抽干净」。
4. **房间与游戏类型可见可绑定**：任意客户端能在**房间列表看到每个房间的游戏类型**；房主**创建房间时可选择游戏**；进入房间后**展示该游戏自己的操作面板**（狼人杀房间观感与现状一致）。
5. **骨架可评审**：交付《如何新增一个游戏》说明 + 最小骨架示例（文档级），评审确认「照此步骤可接入一个新游戏且不触碰既有模块」。
6. **非狼人杀可行性已论证**：文档中给出「谁是卧底」接入所需的扩展点清单，并说明「海龟汤」类非回合制问答玩法预留的口子与后续接入方式，证明抽象层不绑定狼人杀式回合/夜晚机制。

## 2. 用户故事

> 术语沿用现状：房间 / 房主 / 玩家 / 阶段 / 身份 / 邀请码 / 大厅（房间列表）。新增术语：**游戏类型**（房间当前绑定的玩法，如「狼人杀」）。

| # | 角色 | 用户故事 | 验收要点 |
|---|------|----------|----------|
| US-1 | 玩家 | 作为**玩家**，我希望**在房间列表看到每个房间的游戏类型，进入后自动看到该游戏对应的操作面板**，以便不会进错游戏、也不用自己切换界面。 | 列表有「游戏」列（图标 + 显示名）；进入「谁是卧底」房间显示卧底面板而非狼人面板；进入狼人杀房间的观感与现状完全一致。 |
| US-2 | 房主 | 作为**房主**，我希望**创建房间时先选择要玩哪个游戏**，以便和朋友开一局指定游戏。 | 创建房间对话框新增「游戏」选择项，**默认选中狼人杀**（保证现状回归）；创建后房间与该游戏绑定；房间列表该房间显示所选游戏类型。 |
| US-3 | 房主 | 作为**房主**，我希望**在选定游戏后按该游戏规则开局**，以便在同一个房间平台上玩不同玩法。 | 开局动作由所选游戏决定；狼人杀开局行为不变（人数/角色分配/夜晚顺序沿用 `GameRules`）；非狼人杀走自己的开局逻辑。 |
| US-4 | 普通玩家 | 作为**普通玩家**，我希望**进入房间后看到的是通用宿主区（房间号/房主/玩家/聊天）+ 该游戏专属的操作面板**，以便既能聊天看名单，又能按当前游戏操作。 | 通用宿主区（玩家列表、聊天、状态栏）各游戏一致；第三栏「操作面板」随游戏切换；狼人杀沿用现有 `ActionPanel`。 |
| US-5 | 开发者 | 作为**开发者**，我希望**新增一个游戏时只需按固定的接入点清单补齐「游戏元数据 + 游戏逻辑 + 操作协议 + 操作面板」**，不需要改房间/登录/邀请码/重连/主题等既有模块，以便低成本扩展游戏种类。 | 按《如何新增一个游戏》步骤，可在**不修改既有平台模块**的前提下接入一个新游戏；接入点数量不超过 §5.4 约定上限（≤5 类）。 |
| US-6 | 控制台用户 | 作为**控制台用户**，我希望**在房间列表和房间内都能看到当前游戏类型**，以便在无 GUI 环境也能正确进入并操作对应游戏。 | 控制台房间列表每行带游戏类型；创建流程可选择游戏；进入房间后标题提示当前游戏；狼人杀现有指令保持可用。 |

## 5. 关键规则定义

### 5.1 游戏类型标识（机器名 / 显示名 / 图标）

| 属性 | 用途 | 约定 | 示例 |
|------|------|------|------|
| **机器名 `GameId`** | 协议、存储、文件命名 | 小写英文短标识，**稳定不变** | `werewolf` / `undercover` / `turtle_soup` |
| **显示名** | 界面展示 | 中文短名 | `狼人杀` / `谁是卧底` / `海龟汤` |
| **图标** | 列表 / 标题 | 单个 emoji | `🐺` / `🕵️` / `🐢` |
| **简介** | 创建房间下拉 / 图鉴 | 一句话 | 狼人杀＝「经典多人推理对抗」 |

- 以上元数据由**游戏目录/注册表集中声明**；新增游戏即在注册点登记一条。
- 协议层只用机器名，界面层用「显示名 + 图标」；**映射关系集中在共享库**，避免前后台拼写漂移。

### 5.2 房间与游戏的绑定关系

- **一个房间只能绑定一种游戏**，在**创建时确定**（`createroom` 携带 `GameId`）。
- **不允许中途更换游戏**：房间生命周期内游戏类型固定；要换游戏＝退出并新建房间（避免身份 / 阶段 / 玩家状态混用）。
- **缺省与未知处理**：
  - 缺失 `GameId`（旧客户端）→ 服务端**回退 `werewolf`**（与现状一致）。
  - 未知 `GameId`（服务器不支持）→ 创建失败，统一提示「**该游戏不可用**」。

### 5.3 已开局房间能否加入

**沿用现行规则，由框架统一执行，与具体游戏无关**：

| 房间状态 | 可否加入 | 提示 |
|----------|----------|------|
| 等待中 / 已结束待重开（`Waiting` / `GameOver`） | ✅ 可加入 | 受人数上限（`MaxPlayers`）与密码约束 |
| 游戏进行中（`Running`） | ❌ 不可加入 | 「游戏进行中，无法加入」 |

- 各游戏**不需要**自己实现这条门禁；它属于通用宿主能力。

### 5.4 新增一个游戏需要改动的接入点（产品视角清单，细节交给架构师）

> **产品级约束：完成下列 5 类接入点即可新增一个游戏；不需要改动房间管理 / 账号登录 / 邀请码 / 断线重连 / 主题 / 设置 / 大厅与房间列表宿主逻辑。**

| # | 接入点 | 内容 |
|---|--------|------|
| 1 | **登记游戏元数据** | 在游戏目录登记一条：`GameId` / 显示名 / 图标 / 简介 / 人数上下限。 |
| 2 | **实现游戏逻辑模块** | 服务端实现该游戏的开局、阶段推进、接收本游戏操作、判定结束；**狼人杀现有逻辑抽到这里**（主角色的夜晚顺序、女巫、猎人、投票、胜负判定）。 |
| 3 | **声明本游戏操作协议** | 本游戏自己的操作名与负载（狼人杀：`start/night/vote/hunter`；卧底：描述 / 投票等）。 |
| 4 | **提供本游戏操作面板** | GUI 一个面板（挂入「操作面板插槽」）+ 控制台对应指令提示。 |
| 5 | （可选）**声明本游戏规则展示** | 供「设置 / 图鉴」展示规则说明。 |

**非回合制（海龟汤）预留的口子**：抽象层**不假设「必须有固定阶段/回合」**——游戏可自行决定自己的阶段模型，甚至可以**无阶段**（纯聊天 / 事件驱动）。框架只负责：透传该游戏的操作与广播、以及通用的房间 / 玩家 / 聊天能力。海龟汤后续接入时，**复用接入点 1–4**（元数据 + 逻辑模块 + 操作协议 + 面板），**无需新增框架能力**。

**「谁是卧底」未来接入示例（本轮不实现）**：需要用到——① 向每位玩家**私发不同的私有信息**（词条，而非狼人杀的「身份」）；② 描述环节与投票环节（可复用阶段模型）；③ 无夜晚角色动作。结论：可完全由接入点 1–4 覆盖，**不需要新增框架能力**。

### 5.5 兼容性（旧客户端 / 新服务器 与 新客户端 / 旧服务器）

| 场景 | 行为 | 是否要求同步升级 |
|------|------|------------------|
| **旧客户端 → 新服务器** | `createroom` 不带 `GameId` → 回退狼人杀；房间列表多出的游戏字段被旧客户端忽略；狼人杀全部操作语义不变 → **可正常使用** | **不需要**升级客户端 |
| **新客户端 → 旧服务器** | 新客户端创建房间时多带 `GameId`，旧服务器忽略未知字段；房间列表无游戏字段 → 新客户端按「默认狼人杀」展示；狼人杀可正常玩；**新游戏在旧服务器不可用**（列表也不会出现） | **不需要**升级服务器即可继续玩狼人杀 |
| **结论** | **不强制两端同步升级**；但「使用某个新游戏」要求**服务器已支持该游戏**。服务端对缺失 / 未知 `GameId` 的兜底策略见 §5.2。 | —— |

## 6. 待确认问题（含推荐默认值）

> 以下均给出推荐默认值，若无异议将按推荐值实现，不阻塞开发。

| # | 问题 | 推荐默认值 |
|---|------|-----------|
| Q1 | 创建房间时的**游戏选择控件形态**？ | **下拉列表**（每行「图标 + 显示名 + 一句简介」），默认狼人杀；实现轻、扩展性好。卡片式作为 P2。 |
| Q2 | 游戏类型标识用什么？ | **协议用英文机器名（小写），界面用中文显示名 + emoji**；映射集中在共享库，避免拼写漂移。 |
| Q3 | 房间能否**中途更换游戏**？ | **不能**；换游戏＝退出并新建房间。 |
| Q4 | 房间列表窗口标题是否由「狼人杀 · 房间列表」改为中立的「游戏大厅 · 房间列表」？ | **建议改为中立标题**；但这会触及「狼人杀观感零变化」的约束，**请确认**。若必须零变化，则保留原标题、仅在列表内新增「游戏」列。 |
| Q5 | 是否**强制两端同步升级**？ | **不强制**；服务端对缺失 `GameId` 回退狼人杀，未知 `GameId` 拒绝并提示「该游戏不可用」。 |
